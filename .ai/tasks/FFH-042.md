## Required architecture

### 1. One financial engine remains authoritative

Do not implement:
- a second Home affordability model;
- a second Vehicle affordability model;
- a second Windfall waterfall;
- a second Your Plan allocator;
- a second Recommendation Refresh engine;
- a second Money Priority Engine.

Adapters must delegate to the accepted existing functions:
- `evaluateHomeAffordability`;
- `evaluateVehicleAffordability`;
- `allocateWindfall`;
- `evaluateUserPlan`;
- `assessRecommendationRefresh`.

### 2. Generic scenario first, specialized layer second

The adapter boundary must distinguish:
- the baseline authoritative engine;
- the generic FFH-040 scenario engine result;
- the specialized module result.

Where generic ScenarioDefinition operations are present:
1. validate/run them through accepted FFH-040;
2. use the resulting scenario engine as the specialized module's financial basis;
3. do not mutate the baseline or generic scenario result;
4. preserve explicit provenance identifying generic versus specialized effects.

### 3. Home adapter

Build a typed Scenario Lab Home adapter over `evaluateHomeAffordability`.

Requirements:
- accept a typed `HomePurchaseScenario`;
- run against the current generic scenario engine result;
- preserve existing Home validation, missing-data, financing-quality, cash-to-close, reserve, goal, employer-match, Secure, required-goal, and retirement-displacement semantics exactly;
- expose the Home result plus the before/after engine comparison needed by later UI;
- do not translate Home inputs into duplicate generic cash/debt/expense operations;
- do not reimplement mortgage-payment/cash-to-close logic.

### 4. Vehicle adapter

Build a typed Scenario Lab Vehicle adapter over `evaluateVehicleAffordability`.

Requirements:
- accept `VehiclePurchaseScenario`;
- run against the generic scenario engine;
- preserve accepted trade-equity/negative-equity, financing, recurring operating cost, protected cash, goal linkage, employer-match, required-goal, and retirement-displacement semantics;
- expose Vehicle result plus before/after engine comparison;
- no duplicate generic debt/cash/expense representation.

### 5. Windfall adapter

Build the Scenario Lab Windfall adapter over `allocateWindfall`.

Critical ordering:
- Windfall is a post-engine one-time consumer.
- It must start from the FINAL generic scenario engine's immutable `retirementCapacityLedger`.
- Do not convert windfall to profile cash before the engine merely to feed the allocator.
- Do not recreate HSA/IRA/shared retirement capacity already consumed by Existing Cash / Secure / Build.
- uncertain tax treatment must remain held for review under existing accepted semantics.
- unallocated windfall must remain available rather than being forced into taxable investing.

### 6. Your Plan layer

Build an optional final Your Plan layer using `evaluateUserPlan`.

Requirements:
- operate on the current specialized/generic authoritative engine result as applicable;
- treat overrides as allocation choices, not household facts;
- preserve exact allocation IDs;
- disappeared allocation IDs must become superseded/invalid under existing semantics;
- never retarget by display name;
- duplicate user overrides remain invalid;
- funding gap must not be silently clamped or reallocated.

### 7. Recommendation Refresh

Use `assessRecommendationRefresh` for:
- baseline vs generic scenario;
- generic scenario vs Home/Vehicle specialized rerun where the module exposes a resulting engine;
- relevant before/after specialized comparisons;
- Your Plan override-status reconciliation where applicable.

Do not invent new causal claims beyond the accepted refresh/change outputs.

### 8. Conflict detector

Implement a typed, deterministic conflict detector preventing double representation.

At minimum detect/reject ambiguous combinations such as:
- generic one-time cash use for Home cash-to-close plus Home adapter cash-to-close;
- generic new mortgage/debt/recurring housing cost representation plus Home adapter for the same purchase;
- generic vehicle acquisition debt/cash/operating-cost representation plus Vehicle adapter;
- generic cash inflow representing a windfall plus Windfall adapter using the same event;
- generic cash/debt/goal operations that would consume the same stable-ID earmark/reserve as a specialized adapter when the adapter already owns that event;
- duplicate Your Plan overrides for the same allocation ID.

Rules must:
- fail closed;
- use stable IDs / explicit adapter event IDs;
- never infer conflicts from display names;
- avoid false conflicts for independent generic assumptions.

### 9. Specialized contract

Create a versioned typed specialized adapter contract suitable for later App/Data wiring.

It should expose bounded equivalents of:
- specialized scenario definition / intent;
- adapter-specific typed payload;
- explicit event/intent ID;
- current generic scenario result reference/provenance;
- specialized result;
- refresh/comparison result;
- conflict status/issues;
- hypothetical-only provenance.

Exact file/type names may vary.

### 10. Immutable/deterministic behavior

Prove:
- baseline engine remains unchanged;
- generic scenario engine remains unchanged after specialized adapter execution;
- repeated equivalent adapter runs are identical;
- stable input ordering cannot change output;
- conflict results are deterministic;
- all existing module rounding behavior remains authoritative.

### 11. Reconciliation / no reuse

Apply the Financial Engine Reconciliation Gate where specialized modules consume money/capacity.

Directly prove:
- Home cash-to-close cannot reuse protected or unrelated earmarked cash;
- Vehicle cash cannot reuse protected/unrelated cash;
- Windfall begins from post-generic final retirement capacity;
- HSA family/shared/catch-up room is not recreated;
- spousal-IRA shared compensation is not recreated;
- one-time windfall dollars reconcile exactly across reservations/allocations/residual;
- Your Plan monthly allocations reconcile exactly against available monthly capacity;
- no epsilon/tolerance waiver;
- no hidden positive residual clamping;
- generic + specialized conflict cases fail before double counting.

Existing accepted standalone behavior must remain green:
