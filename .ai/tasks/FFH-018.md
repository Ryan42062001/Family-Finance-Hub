# FFH-018 — Documentation-Only CI Efficiency Hardening

Owner: Product & Technical R&D Engineer for discovery/design; implementation owner to be assigned by Manager if approved
State: QUEUED
Execution mode: STANDARD_CHAT_HIGH
Dependency classification: INDEPENDENT research/design; production workflow changes intentionally deferred until current red remediation wave is stable

Task branch: Use isolated Workflow V2 branch if production workflow changes are later approved

## Objective

Reduce waste from documentation-only commits repeatedly triggering the full Foundation CI while preserving an always-present trustworthy required status for production and integration checkpoints.

## Evidence / motivation

During the current FFH-011/FFH-012 shared-branch remediation, Workflow V2 documentation commits repeatedly re-ran the full Foundation CI and inherited the same pre-existing calculation failures. Independent Work-mode analysis identified runs #310–#334 as documentation-triggered repeats rather than owner remediation iterations.

## Discovery requirements

- inspect current `.github/workflows/ci.yml` and any branch/PR status expectations;
- determine a path-aware design that does not leave required checks missing, permanently pending, or trivially bypassable;
- compare options such as an always-running gate job that classifies changes, a cheap docs-only path, reusable workflow/job conditions, or separate lightweight documentation validation;
- ensure production/source/migration/test/package/workflow changes still run all required Foundation CI stages;
- preserve exact-checkpoint evidence semantics used by Workflow V2;
- identify whether GitHub branch/ruleset settings constrain safe implementation.

## Non-goals

- no weakening of production validation;
- no blind `paths-ignore` change that could cause required status checks to disappear;
- no current-branch remediation of FFH-011/FFH-012;
- no financial-policy or application behavior changes.

## Acceptance criteria for discovery

1. Evidence-backed recommended design is produced.
2. Required-check behavior and failure modes are explicitly addressed.
3. Production validation coverage is not weakened.
4. Manager decides whether a separate implementation task is justified.
