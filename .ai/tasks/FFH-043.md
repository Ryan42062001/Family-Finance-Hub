## Required architecture

### 1. Server authority remains unchanged

Preserve FFH-041's accepted trust boundary:
- authenticate server-side;
- derive household authority server-side;
- load a fresh current household baseline for each explicit Run/Rerun;
- never trust a client-supplied household ID, policy version, tax version, or stale baseline as authority;
- validate the versioned baseline fingerprint and fail closed on staleness before specialized execution;
- keep all hypothetical state ephemeral.

Do not weaken any FFH-041 auth/stale/rebase/no-write contract.

### 2. Use the accepted FFH-042 contract directly

Application wiring must invoke the accepted specialized contract/runner rather than reimplementing:
- Home affordability;
- Vehicle affordability;
- Windfall allocation;
- Your Plan;
- Recommendation Refresh;
- generic/specialized conflict detection.

Transport/view-model code may shape data for the UI, but it may not recalculate financial results or silently reinterpret statuses.

### 3. Supported specialized scenario modes

The UI/server boundary may expose at most one specialized financial event per Scenario Lab draft:
- Home;
- Vehicle;
- Windfall;
- none.

Optional Your Plan overrides may layer after the resulting generic/specialized evaluation.

Do not allow the client to construct a combination that bypasses the FFH-042 conflict detector.

### 4. Home editor / result surface

Expose the accepted Home scenario input contract necessary for Scenario Lab v1 and render the accepted result, including:
- readiness / affordability state;
- missing information and warnings;
- financing/cash-to-close/protected-cash information;
- relevant post-engine comparison / Recommendation Refresh output.

Do not recreate mortgage-payment, cash-to-close, reserve, goal, employer-match, or retirement-displacement logic in the UI/server layer.

### 5. Vehicle editor / result surface

Expose the accepted Vehicle scenario input contract necessary for Scenario Lab v1 and render:
- affordability state;
- missing information and warnings;
- acquisition/financing/cash information;
- recurring operating-cost effects;
- relevant post-engine comparison / Recommendation Refresh output.

Do not recreate trade equity, financing, protected cash, goal, employer-match, or retirement-displacement logic.

### 6. Windfall editor / result surface

Expose the accepted Windfall input contract and render:
- gross amount;
- explicit reservations;
- held-for-tax-review amount when applicable;
- allocations/destinations;
- remaining unallocated amount;
- warnings / more-information-needed state.

Preserve that Windfall is post-engine and starts from the final generic scenario engine. Do not convert the same proceeds into generic profile cash or recurring income.

### 7. Your Plan layer

Allow optional stable-allocation-ID overrides over the current scenario result.

Preserve:
- exact allocation IDs;
- active/superseded/invalid status;
- duplicate override failure;
- funding-gap visibility;
- retirement room conflicts/missing-data warnings;
- no display-name retargeting;
- no silent clamping or reallocation.

### 8. Conflict/error presentation

Surface accepted FFH-042 composition issues as structured, user-actionable validation output.

The UI must make it clear when a scenario is invalid because the same event/entity is represented in both generic and specialized layers.

Do not suppress or auto-correct:
- duplicate event representation;
- ambiguous event ownership;
- stable entity overlap;
- duplicate Your Plan overrides;
- unavailable specialized post-engine basis.

### 9. Rebase must refresh entity options

Close the accepted FFH-041 non-blocking follow-on:
after successful explicit rebase, refresh the current bootstrap/stable-ID entity-option data used by editors.

The refreshed UI should:
- show newly added eligible entities;
- remove unrelated deleted entities without requiring a page reload;
- preserve existing draft references only when the stable ID still resolves;
- leave deleted referenced entities unresolved and require user action;
- never retarget by display name.

Server-side stable-ID validation remains authoritative.

### 10. Ephemeral/no-write boundary

Scenario Lab remains in-memory only.

Do not:
- create Scenario Lab tables;
- write scenario drafts/results to Supabase;
- write hypothetical values into household/profile records;
- use localStorage/sessionStorage/IndexedDB as persistence;
- add Apply/Save/Commit Scenario;
- introduce migrations/RLS changes.

### 11. Comparison / explainability

Use the accepted Recommendation Refresh and specialized result payloads to present:
- baseline vs generic scenario changes;
- generic vs Home/Vehicle post-engine changes where available;
- Windfall allocation outcome;
- Your Plan impacts/statuses.

Do not invent causal or policy claims not present in the accepted outputs.

### 12. Accessibility / mobile

Extend FFH-041's accepted accessible/mobile workspace:
- labeled controls for specialized editors;
- keyboard-operable create/edit/run/reset/duplicate/compare/discard;
- semantic invalid/more-information-needed/status messaging;
- live-region announcements where the existing workspace uses them;
- stacked/card comparison on narrow screens;
- no unbounded horizontal matrix.
