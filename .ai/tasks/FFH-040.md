## Objective

Implement the pure financial-domain foundation for Scenario Lab v1 without creating a second financial engine.

Build a typed, immutable Scenario Definition / overlay / runner layer that applies explicit hypothetical assumptions to an accepted Phase-5 baseline and reruns the existing canonical Money Priority Engine.

This task is deliberately Core-only. It must prove that generic Scenario Lab changes can be represented, validated, applied, and reconciled safely before any authenticated route, server action, page, client state, persistence, or specialized Home/Vehicle/Windfall/Your Plan adapter is built.

Canonical product/technical contract:
`.ai/research/rnd/FFH-039_SCENARIO_LAB_PRODUCT_TECHNICAL_CONTRACT.md`

## Required behavior

### 1. One financial engine

Scenario Lab must reuse `runMoneyPriorityEngine`.

Do not implement a second priority waterfall, second retirement-capacity calculation, second goal competition model, or parallel legal-capacity engine.

The scenario runner should:
1. start from an accepted baseline `MoneyPriorityEngineResult` / normalized snapshot;
2. convert through one authoritative normalized-to-raw representation;
3. apply validated typed scenario overrides to an immutable clone;
4. rerun the existing engine with the same explicit policy/as-of-date contract;
5. return the scenario engine result plus structured scenario provenance/status.

### 2. Extract authoritative normalized-to-raw reuse

The existing `money-priority-hypothetical.ts` contains normalized-snapshot-to-raw conversion needed by accepted hypothetical reruns.

Move/extract that conversion into one reusable authoritative pure module rather than copying it into Scenario Lab.

Requirements:
- existing hypothetical behavior remains regression-equivalent;
- no existing raw/normalized financial field is dropped or widened;
- null/unknown semantics remain exact;
- stable IDs remain stable;
- no display-name-based identity logic is introduced.

### 3. Typed Scenario Definition contract

Create a discriminated, versioned Scenario Definition contract for v1.

It must distinguish:
- recurring financial overrides;
- one-time financial events;
- optional future specialized-module intent boundary without implementing specialized adapters;
- explicit scenario-definition version;
- explicit baseline/fingerprint reference field(s) as opaque provenance only, not authorization.

Do not use arbitrary JSON Patch, unrestricted property paths, or untyped object merge semantics.

Runtime validation must fail closed on:
- unknown override/event types;
- duplicate/conflicting targets;
- malformed/nonfinite money;
- invalid enum/date/boolean values;
- references to missing entities;
- protected legal/statutory fields presented through a generic override;
- ambiguous event combinations that would double-count the same money.

### 4. Generic v1 override support

Implement only generic INCLUDE categories that reuse existing accepted semantics:

- existing income source: amount/gross/active replacement;
- explicitly synthetic/additional income source where meaning and amount are supplied;
- existing recurring expense replacement;
- synthetic recurring expense with explicit essential/cash-flow treatment;
- existing debt: supported balance/payment/APR/state changes;
- atomic cash-funded debt payoff;
- goal target/current/date/user-priority/planned-contribution changes already represented by the snapshot contract;
- existing retirement-account scheduled contribution/planning-input changes that do not change statutory facts;
- person planned-retirement-age change;
- existing insurance-exposure changes already represented by normalized inputs;
- planning preference changes already accepted as non-statutory inputs, including explicit known income disruption/end date where supported;
- generic one-time cash inflow;
- generic one-time cash use;
- cash-impact-only large medical event via ordinary one-time/recurring cash-flow semantics.

Job-loss / parental-leave / temporary-income-reduction scenarios are compositions of explicit income changes plus existing known-disruption/end-date inputs. Do not invent severance, unemployment benefits, leave benefits, taxes, statutory entitlements, or recovery dates.

Childcare is an ordinary user-supplied recurring-expense scenario. Do not add dependent-care tax semantics.

### 5. Protected fields / excluded semantics

Generic Scenario Lab overrides must not create or infer protected legal/statutory facts.

At minimum, do not expose generic mutation of:
- HSA legal-spouse authority;
- HSA month eligibility/coverage/evidence;
- HSA last-month/testing-period facts;
- SIMPLE legal plan-limit category;
- IRA/HSA actual YTD contributions;
- filing-status legal eligibility;
- compensation facts whose product meaning is statutory/legal-capacity authority;
- tax-policy version;
- Money Priority policy version;
- any field whose accepted Phase-5 semantics require separate authority.

Baseline unknown remains unknown unless FFH-039 explicitly classifies the changed field as a safe hypothetical planning input.

### 6. Recurring versus one-time separation

Every scenario operation must have an explicit temporal class.

Preserve:
- recurring monthly income/expense/debt/savings effects;
- one-time cash inflow/use;
- one-time cash-funded payoff;
- one-time cash not becoming recurring income;
- recurring changes not becoming artificial account balances.

Atomic multi-effect events must be represented atomically where separate representation could reuse the same dollars.

For the required cash-funded debt payoff:
- cash consumption and debt principal change are one scenario operation;
- it cannot independently consume cash twice;
- insufficient eligible cash / invalid debt references fail clearly.

### 7. Immutable baseline

No Scenario Lab operation may mutate:
- the baseline normalized snapshot;
- the baseline engine result;
- any nested baseline collection/object;
- accepted policy constants.

Tests must directly prove deep baseline immutability across successful, invalid, and repeated scenario runs.

### 8. Determinism / order behavior

Require:
- repeated equivalent scenario runs produce identical financial outputs;
- independent overrides produce the same result regardless of input order;
- stable entity IDs, not display names, determine targeting;
- duplicate/conflicting overrides fail rather than use last-write-wins;
- scenario-definition ordering does not change cent allocation;
- final-cent behavior remains the canonical engine's behavior.

### 9. Unknown-safe behavior

The runner must preserve `more_information_needed` and existing unknown/legal-capacity behavior.

Do not convert null/unknown to:
- zero;
- false;
- an inferred spouse/account fact;
- invented tax/legal eligibility;
- invented contribution room.

Scenario affordability and legal capacity remain separate concepts.

### 10. Reconciliation

Apply `.ai/shared/FINANCIAL_ENGINE_RECONCILIATION_GATE.md`.

Directly prove at least:
- no-op scenario reproduces baseline engine financially;
- exact aggregate-to-destination equality;
- monthly capacity conservation;
- one-time cash conservation;
- retirement account/owner/shared-group capacity conservation;
- Existing Cash -> Secure -> Build staging remains no-reuse;
- spousal-IRA shared compensation cannot be recreated;
- HSA shared/catch-up capacity cannot be recreated;
- exact annual/monthly and odd-cent behavior remain canonical;
- no epsilon/tolerance waiver;
- no hidden residual clamping.

### 11. Existing hypothetical compatibility

Preserve existing accepted behavior for:
- `runHypotheticalMoneyPriorityEngine`;
- Home affordability;
- Vehicle affordability;
- Windfall;
- Your Plan;
- Recommendation Refresh;
- current Phase-5 tests.

FFH-040 may refactor existing hypothetical plumbing only where needed to establish one authoritative reusable conversion/runner boundary. It must not change accepted financial outcomes merely to simplify Scenario Lab.

The Core implementation should expose a stable pure-domain contract suitable for later App/Data use, such as bounded equivalents of:

- scenario override/event discriminated unions;
- structured validation errors/status;
- pure immutable overlay application;
- pure scenario runner;
- baseline/scenario engine results and assumption provenance needed by a later comparison layer.

Exact names/files may differ if the worker proves a cleaner bounded design.
