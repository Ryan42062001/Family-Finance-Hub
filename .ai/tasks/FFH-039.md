## Objective

Define the production-ready product and technical contract for **Phase 6 — Scenario Lab** before any Scenario Lab implementation begins.

Scenario Lab should let a household explore bounded “what-if” changes against its accepted Phase-5 financial baseline while preserving:
- one authoritative baseline snapshot;
- deterministic financial behavior;
- existing legal-capacity / uncertainty semantics;
- explainable before-vs-after results;
- no accidental mutation of the household’s real financial profile;
- no silent invention of missing financial facts.

The repository already contains reusable primitives such as:
- `money-priority-hypothetical`;
- home affordability;
- vehicle affordability;
- Windfall;
- Your Plan;
- Recommendation Refresh;
- the accepted Phase-5 Money Priority Engine.

R&D must determine how these should compose into one coherent Scenario Lab architecture rather than creating another independent financial engine.

## Required behavior

### 1. Product contract

Define a bounded Scenario Lab v1:
- target user jobs;
- supported scenario categories;
- unsupported/deferred categories;
- baseline-versus-scenario comparison model;
- expected result views and explainability;
- scenario lifecycle: create, edit, rerun, reset, duplicate, compare, discard;
- whether scenarios are ephemeral, persisted, or both, with tradeoffs and recommended v1 boundary;
- stale/baseline-change behavior;
- how Scenario Lab interacts with Recommendation Refresh and existing planning tools;
- mobile/accessibility considerations that materially affect architecture.

Do not assume every imaginable “what if” belongs in v1. Prefer the smallest useful deterministic surface.

### 2. Financial-engine reuse contract

Inspect the frozen accepted Phase-5 architecture and specify:
- which existing calculation modules Scenario Lab should call directly;
- whether a scenario should be represented as a clone + bounded overrides, a normalized overlay, or another explicit model;
- how baseline facts and scenario overrides stay distinguishable;
- how nullable/unknown facts propagate;
- how legal/tax capacity is recomputed after scenario changes;
- how recurring and one-time changes are represented without double counting;
- how concrete destination allocations and exact-cent reconciliation remain authoritative;
- how Existing Cash / Secure / Build / Optimize / Windfall / Your Plan interactions are reused without capacity reuse.

Scenario Lab must not create a second parallel priority engine.

### 3. Scenario taxonomy

Evaluate a practical v1 taxonomy. At minimum investigate:
- income/paycheck change;
- recurring expense change;
- one-time cash/windfall;
- debt balance/payment/payoff change;
- savings/goal amount/date/priority change;
- retirement contribution change;
- home affordability / purchase assumptions;
- vehicle affordability / purchase assumptions.

Also evaluate, but do not automatically include:
- job loss;
- parental leave / temporary income reduction;
- new child/dependent;
- childcare;
- insurance changes;
- tax filing/status changes;
- relocation;
- large medical expense;
- refinancing;
- investment-return assumptions;
- retirement-age changes;
- Monte Carlo / probabilistic simulation.

For every category, identify:
- existing supporting data/calculation surfaces;
- missing data;
- financial-policy ownership if new semantics are required;
- implementation complexity;
- risk of misleading outputs;
- v1 recommendation: INCLUDE / DEFER / REQUIRES POLICY.

### 4. Persistence/data architecture

Determine whether v1 requires Supabase schema changes.

If persistence is recommended, propose only the data contract:
- scenario identity/ownership;
- baseline reference or fingerprint;
- override representation;
- result/cache strategy;
- schema/RLS implications;
- versioning/migration strategy;
- delete/reset semantics.

Do not implement or deploy migrations.

If ephemeral client/server scenarios are sufficient for v1, explain why and define how refresh/reload/share behavior should work.

### 5. Safety / correctness boundaries

Define explicit invariants:
- scenario runs never mutate real household facts unless the user explicitly commits through a separate approved workflow;
- scenario overrides never become authoritative legal facts merely because they were entered hypothetically;
- baseline unknown remains unknown unless the scenario explicitly overrides the relevant fact;
- existing protected HSA/SIMPLE/spousal-IRA/retirement-floor/goal-competition semantics remain in force;
- exact financial reconciliation remains required;
- scenarios cannot reuse the same legal/cash capacity across stages;
- scenario result labels distinguish hypothetical assumptions from persisted reality;
- stale scenarios are detectable after baseline changes.

### 6. Architecture and implementation decomposition

Return:
- recommended Scenario Lab v1 architecture;
- proposed page/routes/components;
- server/client boundary;
- calculation API shape;
- persistence decision;
- baseline fingerprint / stale-detection design;
- comparison/diff model;
- test strategy;
- performance considerations;
- observability/debugging needs;
- exact bounded follow-on tasks by permanent role.

R&D may recommend **product/technical** architecture and task decomposition. It must not recommend workflow-system upgrades; Manager owns workflow changes.

### 7. Policy questions

Identify any unresolved financial-policy questions and route them to the correct policy specialist.

Do not answer new statutory/regulatory or financial-priority questions merely to complete the design.
