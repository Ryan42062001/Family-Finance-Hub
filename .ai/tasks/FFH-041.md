## Objective

Build the authenticated, ephemeral Scenario Lab v1 application surface on top of the accepted FFH-040 pure Core contract.

This task owns the server/client application boundary:
- authenticated household baseline loading;
- Scenario Lab page/workspace;
- in-memory draft lifecycle;
- server action orchestration;
- baseline fingerprint/stale detection;
- baseline-versus-scenario result presentation and explainability plumbing;
- safe transport of typed ScenarioDefinition into the Core runner.

This task must not add scenario persistence, Supabase schema, or new financial semantics.

- `.ai/research/rnd/FFH-039_SCENARIO_LAB_PRODUCT_TECHNICAL_CONTRACT.md`
- `.ai/tasks/FFH-040.md`

## Required behavior

### 1. Authenticated route

Create a bounded Scenario Lab route, expected:
`app/scenario-lab/page.tsx`

Requirements:
- authenticate using the existing server-side auth pattern;
- resolve household authority server-side;
- never trust a client-supplied household ID as authority;
- load the current normalized household snapshot through the existing loader;
- run the baseline Money Priority Engine server-side with an explicit as-of date;
- derive a minimal client-safe baseline view/model;
- no profile mutation.

### 2. Server action / scenario run boundary

Create a server-side run action, expected:
`app/scenario-lab/actions.ts`

Every explicit Run/Rerun must:
1. authenticate the caller;
2. derive current household membership/authority server-side;
3. reload the current normalized baseline;
4. recompute current baseline fingerprint/policy basis;
5. compare against the draft's baseline reference;
6. fail closed as `stale_baseline` if mismatched;
7. validate the typed ScenarioDefinition through the accepted Core contract;
8. call the accepted pure scenario runner;
9. return a purpose-built ScenarioRunDTO.

Do not trust:
- client-supplied household authority;
- client-supplied baseline financial facts;
- client-supplied policy/tax versions as authority.

### 3. Baseline fingerprint

Implement the versioned baseline fingerprint contract accepted by FFH-039.

Requirements:
- reuse/extract Recommendation Refresh canonical financial-basis semantics where practical;
- include financially relevant normalized basis plus:
  - Money Priority policy version;
  - planning-assumptions version;
  - tax-policy version;
  - tax year;
  - explicit as-of date;
  - Scenario Lab fingerprint-schema version;
- use a server-generated SHA-256 digest or equivalent deterministic cryptographic digest;
- exclude display-only naming/notes where Recommendation Refresh already treats them as non-financial;
- entity ordering must not create false staleness;
- cent-equivalent normalized values must not create false staleness;
- policy/as-of/tax-version change must create staleness;
- the digest is change detection/provenance only, not authorization.

### 4. Ephemeral draft lifecycle

Implement in-memory only:
- create;
- edit;
- rerun;
- reset;
- duplicate;
- compare;
- discard.

Requirements:
- no database writes;
- no localStorage/sessionStorage/indexedDB persistence;
- no cross-device save/share/history;
- refresh/navigation may discard drafts;
- warn clearly before losing a dirty draft where appropriate;
- duplicate gets a new local scenario ID while preserving typed override intent and baseline reference.

### 5. Rebase/stale behavior

When a baseline becomes stale:
- do not silently rerun against the new baseline;
- show a stale state;
- allow explicit rebase only;
- preserve override intent only when every referenced stable entity ID still exists;
- deleted/replaced entities become unresolved;
- never retarget by display name;
- refresh the baseline reference only after validation;
- rerun only after successful rebase.

### 6. Comparison boundary

Support:
- baseline vs one scenario;
- baseline plus up to two scenario drafts;
- direct scenario-to-scenario comparison only when both share the same current baseline fingerprint and policy basis.

Comparison should expose:
- changed assumptions;
- scenario status;
- feasibility before/after;
- recommendation changes when available;
- allocation deltas when available;
- warnings/missing-data changes;
- explicit hypothetical provenance.

Do not invent causal narrative beyond existing engine/module reasons.

### 7. Explainability / Recommendation Refresh reuse

Use accepted Recommendation Refresh semantics for:
- financial-basis change classification;
- recommendation/allocation changes;
- feasibility changes;
- override-status reconciliation where applicable.

This task may build the generic comparison adapter needed for baseline-vs-generic-scenario results.

It must not yet implement specialized Home/Vehicle/Windfall/Your Plan Scenario Lab adapters. Those remain a later bounded integration task.

### 8. Client workspace

Build a practical accessible/mobile Scenario Lab workspace with bounded generic v1 editors for FFH-040-supported categories.

At minimum support user entry for:
- income/paycheck change;
- recurring expense change;
- explicit additional income;
- childcare as recurring expense;
- debt balance/payment/APR change;
- atomic cash-funded debt payoff;
- goal amount/date/priority/contribution change;
- retirement scheduled contribution/planning-input change;
- planned retirement age;
- insurance exposure values;
- accepted non-statutory planning preferences;
- explicit job-loss / temporary income reduction using user-supplied income + disruption/end date;
- one-time cash inflow;
- one-time generic cash use;
- cash-impact-only medical event.

UI must not expose generic editors for protected legal/statutory fields.

### 9. Protected fields

Do not expose UI or transport authority for:
- HSA legal-spouse authority;
- HSA monthly eligibility/coverage/evidence;
- last-month/testing-period facts;
- SIMPLE plan-limit authority;
- IRA/HSA actual YTD contribution authority;
- filing-status legal eligibility;
- statutory compensation authority;
- tax/policy versions;
- other protected fields excluded by FFH-040.

If malformed client data attempts these fields, the Core validator must still reject it.

### 10. No persistence / no schema

FFH-041 must not:
- add Scenario Lab tables;
- add migrations;
- change RLS;
- change live Supabase;
- persist drafts/results;
- cache a second financial truth.

Existing household reads are allowed through the accepted loader/auth pattern.

### 11. No apply-to-profile

Scenario Lab v1 has no operation that writes hypothetical assumptions into authoritative household financial facts.

Do not add:
- Apply Scenario;
- Save to Profile;
- Commit Scenario;
- implicit write-through actions.

### 12. Performance

- explicit Run/Rerun only; do not execute the full engine on every keystroke;
- one baseline reload per run;
- no Supabase query per override;
- baseline engine should be computed once per request;
- return purpose-built DTOs, not unrelated server/internal state;
- comparison cap: baseline + two scenarios.

### 13. Accessibility/mobile

At minimum:
- all controls have explicit labels/units;
- changed values cannot rely on color alone;
- stale/invalid/missing states use semantic text;
- no drag-only operations;
- keyboard-accessible create/duplicate/compare/discard;
- focus/result announcement after run;
- mobile comparison uses cards/stacked layout rather than an unbounded horizontal matrix.

### 14. Security / privacy

- no raw household financial content in logs;
- no scenario title/notes or detailed balances logged for diagnostics;
- structured logging may include only non-sensitive metadata such as correlation ID, definition version, override count, status class, elapsed time, policy versions, and fingerprint prefix;
- unauthenticated run rejected;
- user cannot scenario another household by submitting an ID.
