### New independent non-blocking observations

**TMA-051-R01-01 — LOW — encoded control characters remain representable in accepted internal paths.** A direct helper run accepts \`/%0d%0aevil.example\` as \`https://family-finance-hub-ten-brown.vercel.app/%0d%0aevil.example\`. The returned URL contains no raw CR/LF, does not change origin, and the final \`Location\` in the synthetic handler likewise remains percent-encoded; no response-splitting or external navigation was demonstrated. This is narrower than the prior HIGH redirect issue. Follow-up hardening may reject percent-encoded control characters if URL decoding/logging/downstream routing requires it; do not describe it as proven remote exploitation.

**TMA-051-R01-02 — LOW / DEPLOYMENT-DEPENDENT ORIGIN TRUST.** \`safeInternalDestination\` resolves against \`requestUrl.origin\`; a synthetic request URL on \`https://untrusted.example\` yields a same-*request*-origin redirect there. The helper has no independent configured-app-origin pin. Whether an attacker can inject an arbitrary Host/forwarded host that the actual deployment accepts is **unverified**, not a demonstrated Vercel open-redirect exploit. Before production release verify accepted hostnames, edge/proxy Host/forwarded-host normalization, canonical HTTPS app URL and redirect origin through actual safe requests. If untrusted Host can influence the redirect origin, return to bounded remediation before release; otherwise retain as deployment evidence only.
